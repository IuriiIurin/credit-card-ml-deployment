# План A/B тестирования

## Концепция теста

Сравниваем две версии модели прогнозирования дефолта по кредитным картам:
- Контрольная группа (v1): LogisticRegression - простая линейная модель, текущая версия в продакшене
- Тестовая группа (v2): RandomForestClassifier - ансамблевая модель, потенциально лучше улавливает нелинейные зависимости в данных

Цель теста - определить, даёт ли v2 статистически значимое улучшение качества предсказания дефолтов по сравнению с v1.

## Разделение трафика

Случайное распределение 50/50, каждый пользователь случайно (но стабильно по user_id) направляется к v1 или v2. 
Такое разделение выбрано по двум причинам:
- Одинаковый размер выборок обеспечивает максимальную статистическую мощность теста
- Случайное распределение исключает систематическую ошибку выборки, например когда к одной модели попадают только клиенты определённого типа

По результатам EDA, я выяснил, что датасет несбалансирован (78% - нет дефолта, 22% - дефолт).
При случайном разделении 50/50 дисбаланс классов сохраняется в обеих группах примерно одинаково, что обеспечивает честное сравнение моделей.
Обе модели обучены с параметром class_weight='balanced' для компенсации дисбаланса.

## Продолжительность теста

Минимум 2 недели для накопления достаточной статистики. Обоснование:
- Слишком короткий тест может дать случайный результат из-за малой выборки
- 2 недели охватывают возможные недельные циклы в поведении клиентов (например, активность в начале и конце месяца)
- При трафике около 1000 запросов в день за 2 недели накопим ~14000 наблюдений на каждую группу - достаточно для статистически значимых выводов
- Если трафик ниже - тест продлевается до накопления минимум 5000 наблюдений на каждую группу

## Метрики оценки

Основная метрика: F1-score для класса дефолта (класс 1) потому, что учитывает одновременно precision и recall, 
что важно при дисбалансе классов. Accuracy была бы обманчива, так как модель предсказывающая всегда 0 даст accuracy=78%.

Дополнительная метрика: Recall - важнее для банка потому, что пропуск реального дефолта (ошибка 2 рода) означает выдачу кредита клиенту который не вернёт деньги. 
Это прямые финансовые потери, которые дороже чем отказ надёжному клиенту (ошибка 1 рода).

Текущие значения на тестовой выборке:
- v1 (LogisticRegression): F1=0.48, Recall=0.65
- v2 (RandomForestClassifier): требует оценки в боевых условиях

## Статистический анализ

Гипотезы:
- H0: модель v2 не лучше v1 по F1-score (F1_v2 <= F1_v1)
- H1: модель v2 лучше v1 по F1-score (F1_v2 > F1_v1)

Используем односторонний тест, так как нас интересует только улучшение, ухудшение v2 относительно v1 означает что H0 не отвергается и v2 не принимается в продакшн.

Для сравнения моделей используем два подхода:
1. Bootstrap для сравнения F1-score между группами.
   F1 не является нормально распределённой метрикой, поэтому t-test некорректен. 
   Bootstrap позволяет построить распределение F1 без предположений о нормальности: многократно сэмплируем предсказания с возвращением и считаем F1 на каждой итерации.

2. z-test для пропорций для сравнения Recall между группами.
   Recall = TP / (TP + FN) - это доля реальных дефолтов, которые модель правильно предсказала. Сравнение двух таких долей корректно делать через z-test для пропорций.

Доверительные интервалы:
- Строим 95% доверительные интервалы для F1 (через bootstrap) и Recall (через z-test) каждой группы.

Критерий успешности:
- p-value < 0.05 по обоим тестам
- Отвергаем H0 - F1 группы v2 статистически значимо выше чем у v1
- Recall группы v2 не хуже чем у v1

## Разбиение трафика и предотвращение leakage

Разбиение должно быть по user_id, а не по запросам. Если делить случайно по каждому запросу - один пользователь может попасть и в v1 и в v2, 
что нарушает независимость наблюдений и создаёт поведенческий leakage.

Правильный подход, фиксировать группу по user_id:
- hash(user_id) % 2 == 0 - группа v1
- hash(user_id) % 2 == 1 - группа v2

Это гарантирует что каждый пользователь всегда видит только одну модель и группы остаются независимыми.

## Бизнес-метрики

1. Снижение финансовых потерь:
   Считаем сумму кредитов выданных клиентам которые в итоге допустили дефолт (False Negative). 
   Чем меньше эта сумма, тем лучше модель защищает банк от потерь. Рассчитывается как: сумма LIMIT_BAL для всех FN предсказаний.

2. Доля одобренных заявок при том же уровне риска:
   Считаем долю клиентов которым одобрили кредит (prediction=0) среди тех, кто реально не допустил дефолт (True Negative). 
   Чем выше эта доля, тем меньше банк теряет потенциальных надёжных клиентов. Рассчитывается как: TN / (TN + FP).

Победителем теста считается модель которая одновременно:
- Снижает финансовые потери (меньше FN)
- Сохраняет или увеличивает долю одобренных надёжных клиентов

## Связь с архитектурой

API поддерживает выбор версии модели через параметр model_version в запросе:
- model_version: "v1" направляет запрос к LogisticRegression
- model_version: "v2" направляет запрос к RandomForestClassifier

Пример реализации случайного разделения трафика 50/50 на стороне клиента:

Для каждого пользователя вычисляем стабильный номер группы (0-99) на основе его user_id. 
Это гарантирует что один пользователь всегда попадает в одну и ту же группу независимо от количества запросов,
что исключает leakage между группами и обеспечивает независимость наблюдений.

import hashlib                                                          # используем для стабильного хеширования

def stable_hash(user_id):                                               # функция для детерминированного хеша
    return int(hashlib.md5(str(user_id).encode()).hexdigest(), 16)      # переводим hex в число

user_id = <user_id>                                                     # уникальный идентификатор пользователя
bucket = stable_hash(user_id) % 100                                     # получаем число от 0 до 99
version = "v1" if bucket < 50 else "v2"                                 # делим пользователей 50/50

response = requests.post(url, json={<..данные клиента..>, "user_id": user_id, "model_version": version})

бе модели загружены в память при старте сервиса и доступны без дополнительных задержек. 
Все запросы и ответы логируются в logs/api.log для последующего анализа результатов теста.
